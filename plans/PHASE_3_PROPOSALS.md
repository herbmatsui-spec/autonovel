# Phase 3: コア軽量化とEasy Mode研ぎ澄まし（Pragmatic Streamlining & UX） - 9つの提案

**ベース**: `plans/PHASE_ROADMAP_MASTER.md` の Phase 3 セクション（4つの既存タスク）に基づき、ゴール「1話あたり数十円以内・1分以内での生成完走と、最も価値の高いユーザー体験（Easy Mode）の実現」に沿って、さらに5項目を追加した計9つの提案です。

---

### Phase 3 提案（計9項目）

| # | 提案項目 | 目的・根拠 |
|---|----------|-----------|
| 1 | **8専門オーディターの集約**: 静的ルール（形式・禁則チェック）＋ 1回の一括LLMコール（定性監査）への再編 | 既存タスク。監査コストと遅延を1/8に圧縮し、品質基準を維持しながらスループット向上。 |
| 2 | **PDCAサイクルのスリム化**: 原則1発生成 ＋ 致命的不整合時のみ局所リライト（1回制限） | 既存タスク。コスト爆発を防ぎつつ、文章品質の劣化を最小限に抑える現実的バランス点。 |
| 3 | **Easy Mode（かんたんモード）の完成**: ブラウザから迷わず本文生成〜ZIP/EPUB納品まで完走するフローの堅牢化 | 既存タスク。価値の高いUXを提供し、非技術者ユーザーの採用障壁を除去。 |
| 4 | **トークン消費・生成速度のベンチマーク計測** | 既存タスク。改善効果の定量評価基盤と、Phase 4 の商用化判断材料を提供。 |
| **5** | **プロンプトテンプレートの標準化とバージョン管理（`prompts/` ディレクトリ整理・`prompt-versioning` 導入）** | プロンプトの属人化防止と改善履歴の可視化。A/B テストによる客観的品質評価を可能にし、属人知を組織知に転換。 |
| **6** | **フォールバック機構の実装（LLM失敗時の静的ルールベース代替生成）** | 商用レベルの信頼性確保。LLM プロバイダーの一時的不調やレートリミット時でもサービス継続性を保ち、ユーザー体験の低下を防止。 |
| **7** | **段階的品質フィードバックUI（リアルタイムプレビュー＋段階的改善提案）** | ユーザーが生成過程を理解・参加できる仕組み。信頼性と満足度向上のため、黒箱感を解消し、コントロール感を提供。 |
| **8** | **キャッシュレイヤーの導入（同様プロンプト・パラメータの結果キャッシュおよび類似検索ベースのセマンティックキャッシュ）** | 同じまたは類似リクエストの重複処理を削減し、レイテンシーとコストをさらに削減。特にユーザーが微調整を繰り返す場合に効果大。 |
| **9** | **マルチモーダル入力サポートの検討・プロトタイプ（画像・音声からのストーリープロンプト生成）** | Easy Mode の魅力向上とアクセシビリティ改善。テキスト入力に苦手意識があるユーザーや、ビジュアル思考を好むクリエイターの取り込みを狙う。 |

### 採用時の次のアクション案

1. **項目 5・6・7・8・9** を `plans/PHASE_ROADMAP_MASTER.md` の Phase 3 セクションに追記（番号を振り直し）
2. **項目 5 用ディレクトリ構造** 提案:
   ```
   prompts/
   ├── base/
   │   ├── system.yaml          # 基本システムプロンプト
   │   ├── auditor_unified.yaml # 統合オーディタープロンプト
   │   └── local_polish.yaml    # 局所推敲プロンプト
   ├── v1.0/                    # バージョン別ディレクトリ
   │   ├── system.yaml
   │   └── auditor_unified.yaml
   └── latest/                  # 現在使用中のバージョンへのシンボリックリンクまたは参照
   ```
3. **項目 6 用フォールバック設計**:
   - LLM API エラーまたはタイムアウト時
   - 静的ルールベースのストーリージェネレーター（テンプレート＋ランダム要素）にフォールバック
   - 品質は落ちるが「生成されない」よりはマシという商用判断
   - フォールバック発生時は監視・アラートを発信し、可能なら人間-in-the-loop をトリガー
4. **項目 7 用 UI フロー検討**:
   - 生成開始後 10-30秒ごとに中間結果を表示
   - ユーザーが「この方向で良い」と承認すれば続行、「方向修正」すればプロンプト調整して再生成
   - 最終出力前に「この文章のここが気になる」ポイント指摘で局所推敲をトリガー
5. **項目 8 用 キャッシュ戦略**:
   - **Exact Cache**: 同じプロンプト・パラメータ・シードなら完全キャッシュ（ハッシュキー）
   - **Semantic Cache**: 類似意味のプロンプトをベクトル検索で発見し、その結果を適用・調整
   - キャッシュ無効化ポリシー: 時間ベース（TTL）またはプロンプトテンプレートバージョン変更時
6. **項目 9 用 マルチモーダル検証手順**:
   - 画像入力 → 画像キャプショニングモデル（BLIP等） → ストーリープロンプト生成
   - 音声入力 → 音声認識（Whisper等） → テキスト → 既存フロー
   - まずはプロトタイプ段階で品質とコストを検証し、Phase 4 以降のオプション機能として位置付け

### 注意点・前提条件

- **Phase 2 完了済み**: 重複コード削除・単一アーキテクチャが前提。これにより、新機能追加時の影響範囲が予測可能。
- **Phase 1 完了済み**: テストスイートが常時 GREEN 状態。リグレッションなく変更を加えられる基盤がある。
- **LLM コスト意識**: 全提案は「1話あたり数十円以内」というハード制約を前提とする。ベンチマーク（項目4）で効果測定必須。

どの項目から着手するか、または優先順位調整が必要であれば指示ください。  
（注: Easy Mode の完成は Phase 3 の花形機能であり、ユーザーフィードバックを早期に得られるよう、垂直スライスで実装することを推奨します）
