## 5. 単体テスト要件（テストケース）

### 5.1 テスト戦略
- テストフレームワーク: pytest
- モックライブラリ: unittest.mock
- カバレッジ目標: 80%以上（コアロジックは90%以上）
- テスト実行: `pytest tests/ -v`
- カバレッジ測定: `pytest --cov=./src tests/`

### 5.2 テストケース分類

#### A. 正常系テストケース
各モジュールの主要機能が期待通りに動作することを確認

#### B. 異常系テストケース
各種エラー条件下での適切な例外処理を確認

#### C. 境界値テストケース
入力値の境界での動作を確認

#### D. 統合テストケース
モジュール間の連携動作を確認

### 5.3 モジュール別テストケース要件

#### A. USB監視モジュール (usb_monitor.py)
**正常系:**
- USBドライブの挿入を検出してイベントを発火
- ファイル作成イベントを正しくフィルタリング (.pdf のみ)
- 複数の監視パスを同時に処理
- ファイル名の大小文字を区別しないフィルタリング

**異常系:**
- アクセスできないドライブが指定された場合の処理
- 監視中のドライブが突然取り外された場合の処理
- 権限不足でディレクトリを読めない場合の処理
- 無効なパスが指定された場合の処理

**境界値:**
- 非常に長いファイル名（255文字近く）
- Unicodeファイル名（日本語、絵文字など）
- 隠しファイルとシステムファイルの扱い

#### B. PDF処理モジュール (pdf_processor.py)
**正常系:**
- 有効なPDFファイルから画像を抽出できる
- 各ページが正しい解像度で変換される
- メタデータが正しく抽出できる（ページ数など）
- 空のページも適切に処理される

**異常系:**
- 存在しないファイルパスが指定された場合
- ファイルがPDFでない場合（画像ファイルなど）
- 暗号化されたPDFファイル（パスワード必要）
- 破損したPDFファイル（ヘッダーが壊れているなど）
- 0バイトのファイル

**境界値:**
- 1ページのPDF
- 非常に大きなページ数のPDF（1000ページ以上）
- 极端に大きなページサイズのPDF
- 极端に小さなページサイズのPDF

#### C. OCR処理モジュール (ocr_processor.py)
**正常系:**
- 明瞭な印刷体テキストを正確に認識
- 手書き日本語テキストをある程度の精度で認識
- 英数字混在テキストを正常に処理
- 信頼度スコアが正しく返される
- 複数ページの処理が順番通りに行われる

**異常系:**
- Google Cloud Vision APIが利用不可の場合
- 認証情報が無効または期限切れの場合
- リクエストがタイムアウトした場合
- レートリミットに達した場合
- 送信した画像がサポートされていない形式の場合

**境界値:**
- 完全に白紙の画像
- 完全に黒い画像
- 極小のテキスト（フォントサイズ4pt以下）
- 極大のテキスト（画像全体を覆う文字）
- 90度、180度、270度回転したテキスト

#### D. テキスト処理モジュール (text_processor.py)
**正常系:**
- 複数のOCR結果を正しく結合
- 改行とページ区切りを適切に処理
- 余分な空白文字を除去しつつ、必要な構造は保持
- 日本語テキストでの空白処理が適切
- 全角・半角文字の正規化が正しく行われる

**異常系:**
- 空のOCR結果リストが渡された場合
- Noneが含まれたOCR結果リストが渡された場合
- 不正な形式のOCR結果オブジェクトが渡された場合

**境界値:**
- 単一文字のみのテキスト
- 非常に長いテキスト（100,000文字以上）
- 特殊文字のみのテキスト（記号、絵文字など）
- 改行しか含まないテキスト

#### E. Gemini処理モジュール (gemini_processor.py)
**正常系:**
- 簡単なテキストを要約できる
- 重要なポイントを抽出できる
- 初心者向けに専門用語を平易な言語に言い換える
- 指定された長さや形式で出力を生成する
- マークダウン形式で適切にフォーマットする

**異常系:**
- Gemini APIが利用不可の場合
- APIキーが無効または quota超過の場合
- リクエストがタイムアウトした場合
- セーフティフィルターによってブロックされた場合
- レートリミットに達した場合

**境界値:**
- 空のテキスト入力
- 非常に長いテキスト入力（トークン制限を超える）
- 特殊文字のみのテキスト
- 数字と記号しか含まないテキスト
- 同じ単語の繰り返しのみのテキスト

#### F. 出力生成モジュール
**PDF生成 (pdf_generator.py):**
- 正常系: シンプルなテキストからPDFを生成、見出しと本文を適切にフォーマット、日本語文字を正しく表示
- 異常系: フォントファイルが見つからない場合、ディスク書き込みエラーの場合
- 境界値: 非常に長い単語（折り返しが発生）、極端に長いドキュメント

**Word生成 (docx_generator.py):**
- 正常基: 基本的なスタイル適用、箇条書きの生成、画像の埋め込み（将来の拡張性を考慮）
- 異常系: テンプレートエラー、ディスク書き込みエラー
- 境界値: 非常に深いネストの箇条書き、非常に長い見出しテキスト

**音声生成 (audio_generator.py):**
- 正常系: テキストから自然な音声を生成、指定された話速とピッチで再生可能な音声ファイルを作成、SSMLタグを適切に処理
- 異常系: TTS API利用不可、無効な言語コード、テキストが長すぎる場合の分割処理
- 境界値: 空のテキストリスト、1文字のテキスト、非常に長い単一文章（チャンク分割必要）

#### G. オーケストレーター (orchestrator.py)
**正常系:**
- ファイル検出から処理完了までの一連のフロー
- 成功時の状態遷移と結果記録
- 複数ファイルの順次処理
- グレースフルシャットダウン

**異常系:**
- 各ステージでの例外発生時の適切なエラーハンドリング
- 一時ファイルのクリーンアップ確実性
- リトライロジックの動作（一時的エラーに対する）
- 同時処理数の制限機能

**境界値:**
- 非常に大容量のファイル（メモリ使用量の監視）
- 極端に短い処理時間が必要なファイル
- ファイル名に特殊文字が含まれる場合の処理

### 5.4 テスト実装ガイドライン

#### A. モックの使用原則
1. 外部サービス（Google Cloud APIなど）は必ずモックを使用
2. ファイルI/Oは一時ディレクトリを使用して実際のファイル操作を行う（可能な限り）
3. 時間依存の処理は時間をモック可能にする
4. システム依存（プラットフォーム固有の機能）は抽象化してモック可能にする

#### B. テストデータの管理
1. テスト用のサンプルPDFファイルをリポジトリに含める（小サイズ、様々な特徴を持つもの）
2. テスト用の画像ファイルを用意する（OCRテスト用）
3. テスト用の期待されるOCR結果をJSONまたはピクルで保存
4. テスト用の期待されるGemini応答をJSONで保存

#### C. アサーションのベストプラクティス
1. 可能な限り具体的なアサーションを使用する（例: equalではなく、具体的なフィールド値をチェック）
2. 例外の種類とメッセージを両方チェックする
3. コレクションの場合は、順序を含めて等価性をチェックするか、ソートして比較する
4. 浮動小数点数の比較では、適切な許容誤差を設定する
5. ファイル出力のテストでは、存在チェックと内容チェックの両方を行う

#### D. テストの命名規則
1. テストクラス: `Test[ClassName]`
2. テストメソッド: `test_[method_name]_[condition]_[expected_result]`
3. 例: `test_process_pdf_with_valid_file_returns_images`
4. 例: `test_perform_ocr_on_image_with_invalid_api_key_raises_OCRError`

#### E. テストファイルの構成
```
tests/
├── __init__.py
├── conftest.py                 # フィクスチャと共有設定
├── test_usb_monitor.py
├── test_pdf_processor.py
├── test_ocr_processor.py
├── test_text_processor.py
├── test_gemini_processor.py
├── test_pdf_generator.py
├── test_docx_generator.py
├── test_audio_generator.py
├── test_orchestrator.py
├── test_logger.py
└── test_error_handler.py
```

#### F. フィクスチャの使用（conftest.py）
1. 一時ディレクトリのフィクスチャ
2. テスト用設定オブジェクトのフィクスチャ
3. モックAPIクライアントのフィクスチャ
4. テスト用サンプルデータのフィクスチャ
5. ロガーのフィクスチャ（テスト中は出力を抑制）

#### G. パフォーマンステスト（オプションだが推奨）
1. 大きなファイルの処理時間を測定
2. メモリ使用量の増加を監視
3. 同時処理数によるスループットの変化を測定
4. これらはCIではなく夜間ビルドやリリース前のベンチマークとして実行

### 5.5 カバレッジ要件
- 各モジュールファイル: 最低70% カバレッジ
- コアロジック（OCR、Gemini連携、オーケストレーター）: 90%以上
- 例外パス: 50%以上（発生が難しいため）
- エッジケース処理: 75%以上

### 5.6 CI/CDパイプラインでのテスト
1. プルリクエスト時に自動的にテストを実行
2. カバレッジがThreshold未満の場合は警告を出す（ブロックはしない）
3. メインブランドへのマージ時は、カバレッジが80%以上を要求（ブロックする）
4. テスト失敗はマージをブロック
5. セキュリティスキャンとライセンスチェックも併実施

### 5.7 テスト実行のベストプラクティス
1. ローカル開発時は、`pytest -x` で最初の失敗で停止
2. カバレッジを確認したい時は、`pytest --cov=./src --cov-report=html`
3. 特定のモジュールのみテストしたい時は、`pytest tests/test_[module_name].py`
4. 詳細な出力が欲しい時は、`pytest -v`
5. 実行時間のかかるテストは、`pytest -m "not slow"` で除外可能（マーカーを付ける）

このテスト戦略により、変更による regresion を早期に検出し、品質の高いリリースを維持することができます。
