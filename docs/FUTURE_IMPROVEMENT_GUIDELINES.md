# AutoNovel 今後の改善指針

本ドキュメントは、AI支援小説執筆およびマルチエージェントシステムに関する最新の研究知見に基づき、AutoNovelプロジェクトの今後の改善方向性を示すものです。以下の9つの改善提案は、創造性、品質、効率性、拡張性の観点から優先順位付けられています。

## 1. ブラインドピアレビュー方式のフィードバックループ導入

現在のマルチエージェントシステムでは、エージェント間の過剰な情報共有が同質化を引き起こし、創造的発散を抑制している可能性があります。LLM Review論文（2026年）が示す通り、クリエイティブなタスクにおいては、エージェントが同僚の修正プロセスを観察することなく、ターゲットされたフィードバックのみを受け取るブラインドピアレビュー方式が効果的です。

AutoNovelにおける具体的な適用として、WritingAgentが生成した本文に対するAuditAgentの評価プロセスを修正します。現在の設計では、AuditAgentが一貫性やカタルシス等を評価する際、他のエージェント（PlanningAgent、PlotAgent等）の出力も参照可能ですが、これにより次第に特定のストーリー傾向へ収束しやすくなります。ブラインドピアレビューでは、各エージェントは自身の出力に対するフィードバックのみを受け取り、他エージェントが同じフィードバックに対してどのように修正したかを一切参照しない実装が必要です。

例えば、PlanningAgentが提案した3案企画ガチャの各案に対して、独立したAuditAgentインスタンスがそれぞれフィードバックを提供するが、他の企画案の評価結果は見せない構造にします。これにより、エージェントは外部からの客観的批判を得つつ、独自の創造的方向性を維持できます。実装では、EventBusを介したフィードバック配信メカニズムを修正し、フィードバックオブジェクトに「参照禁止フラグ」を追加します。ワーカータスク（generation_tasks.py）では、このフラグが設定されている場合、他エージェントの最新状態へのアクセスを一時的にブロックする仕組みを構築します。これにより、創造性の多様性を保ちつつ、論理的整合性や読者フック診断といった品質管理機能は損なわない状態を実現できます。特に長編連載では、中期以降の設定の矛盾を防ぐGraphRAGの恩恵を受けながら、初期企画段階での創造的探索空間を拡張できる効果が期待されます。

## 2. 4階層コンテキスト圧縮機構の実装

長編小説生成における大きな課題の一つは、プロンプトサイズの肥大化によるLLMのコンテキストウィンドウ制限とコスト増大です。フィクショナルワールドビルディング論文（2026年）のAutoWorldBuilderが実装した4階層コンテキスト圧縮機構は、トークン使用量を約90%削減しながら関連情報の保持率を向上させる有効なアプローチです。

AutoNovelの現在のGraphRAGパイプライン（graph_pipeline.py, age_client.py, rag_service.py）では、ContextBuilderAgentが直近エピソードのダイジェストとWorld Bibleから関連エンティティを抽出し、プロンプトに注入していますが、長編になるとプロンプトサイズが肥大化し、効率性が低下します。4階層圧縮は以下のように構成されます：第1階層で抽出生テキストのキーフレーズ抽出（例：TF-IDF、KeyBERT、またはrank-bm25）、第2階層でエンティティ関係のサブグラフ抽出（Apache AGEでの2-hop以内の関係に制限し、関連性スコアに基づくエッジプリューニング）、第3階層で抽出事実の抽象化・カテゴリ化（例：「主人公の剣技」→「武術スキル」や「王都の政治構造」→「統治システム」など、概念レベルに一般化）、第4階層で抽象概念の重要度スコアリングに基づく動的トリミング（重要度が低い抽象概念を除去）。

実装では、src/agents/context_builder_agent.pyのbuild_contextメソッドを拡張し、圧縮階層をパラメータ化します。各階層では、HuggingFaceの要約モデル（facebook/bart-large-cnn）やカスタムルールベース抽出器を使用し、圧縮率と情報保持のトレードオフを制御することが可能になります。特に、GraphRAGから取得するエンティティの関係性情報については、第2階層で関連性スコア（共起頻度・パス長・関係タイプの重要度）に基づくエッジプリューニングを行い、第3階層で関係タイプの階層的グループ化（例：「師弟関係」「敵対関係」「恋愛関係」を「人間関係」に統合し、さらに「指導関係」「対立関係」「親密関係」などのサブカテゴリに分類）を実施します。

これにより、同等の情報量を維持しつつプロンプトトークン数を60-70%削減でき、長編生成時のコスト削減と同時処理能力の向上が見込まれます。さらに、圧縮過程で生成される中間表現をキャッシュ化（Redis）すれば、類似シーンの文脈構築を高速化でき、繰り返し発生するシーンタイプ（戦闘シーン、日常会話、移動描写など）に対する応答性も向上します。この機構により、同じ情報量でもより長い時系列の文脈を参照可能になるため、長編での伏線の効果的な設置と回収も向上するでしょう。

## 3. 専門的オーディターエージェントによるマルチレイヤー品質保証

現在のAuditAgentは機能別に分割されたサブモジュールを束ねたファサードパターンですが、評価が逐次的かつ固定的な重み付けであるため、多面的な品質問題を見逃す可能性があります。フィクショナルワールドビルディング論文の専門的オーディターシステム（8名のスペシャリストによる並列評価）を適用することで、品質評価の多角性と信頼性を大幅に向上させることができます。

専門的オーディターアーキテクチャでは、以下のような独立したエージェントを並列実行させます：①一貫性オーディター（キャラクター行動・世界観ルール・タイムラインの論理的整合性検出）、②創造性オーディター（新規表現・比喩・言い回しの多様性・独創性評価）、③読者フックオーディター（冒頭の「謎・違和感・危機」強度と末尾の「クリフハンガー」スコアリング）、④感情曲線オーディター（カタルシス達成度・テンション変動の適切性・感情の起伏評価）、⑤文体オーディター（口調一貫性・文体DNA遵守・語彙・文構造のスタイル一貫性）、⑥事実正確性オーディター（GraphRAG参照情報との整合性・歴史・文化的正確性・用語の適切性）、⑦構造オーディター（章構成・プロットツリーの論理的流れ・テンポ・起承転結の適切性）、⑧マルチモーダル適合性オーディター（挿絵プロンプトと本文描写の情報量・焦点・感情トーンの整合性）。

各オーディターは標準インターフェースを実装し、AgentResultオブジェクト（スコア、具体的フィードバック、修正提案）を返却します。Orchestratorがこれらの結果を重み付け集約し、最終的な品質判定を行います。重みは作品ジャンル（文芸 vs エンターテインメント vs 教育）や制作フェーズ（企画段階では創造性重視、執筆中期では一貫性重視、終盤ではカタルシス重視等）に応じて動的に調整可能とし、設定ファイル（config/audit_weights.yaml）で管理します。

実装では、src/agents/audit_agent.pyを基底クラスAuditAgentとし、各専門オーディターを継承させた具体的クラス（ConsistencyAuditor, CreativityAuditor等）を作成します。EventBusを介して並列実行をトリガーし（audit.startedイベントで各オーディターを起動）、結果集約のために新しいAuditAggregatorサービスをsrc/services/audit_aggregator.pyに追加します。これにより、単一のAuditAgentでは見落としがちな多面的品質問題（例：論理的には整合しているが読者フックが弱い、または創造性は高いが文体が一貫していない、または事実は正確だが感情の動きが機械的）を検出できるようになります。

さらに、各オーディターの評価結果を時系列で保存すれば、執筆プロセスにおける品質傾向の分析が可能となり（例：創造性スコアが時間とともに低下する傾向がある場合、Promptの多様性を増すトリガーに）、自動的な改善提案の精度向上にも寄与します。このマルチレイヤーアプローチにより、品質評価の信頼性と具体的な改善方向性の示唆が両立します。

## 4. スキル駆動型エージェントアーキテクチャによる拡張性向上性向上

AutoNovelの現在のエージェント実装は機能別に分割されているものの、新しいエージェントタイプを追加する際にはorchestrator.pyのAgentName enum、event_bus.pyのイベントタイプ、ワークフロー定義の修正が必要であり、ジャンル固有の要件や実験的機能への対応が遅延しています。フィクショナルワールドビルディング論文のスキル駆動マルチエージェントアーキテクチャは、ゼロコードで新しい専門エージェントを追加可能にし、システムの適応性と機能拡張性を radikally 向上させます。

スキル駆動アーキテクチャでは、エージェントを「スキル」の集合として定義し、各スキルは標準インターフェース（execute(context: AgentContext) -> AgentResult）を実装します。これにより、新しい機能はスキルプラグインとしてパッケージングされ、設定ファイルで有効/無効を切り替えるだけで利用可能になります。このアプローチの核は、エージェントの機能を細粒度の、再利用可能なコンポーネントに分解することにあります。

実装では、src/agents/skill_base.pyに抽象基底クラスSkillAgentを定義し（executeメソッドを抽象メソッドとする）、既存エージェント（PlanningAgent、WritingAgent等）をこの基底クラスを継承する形でリファクタリングします。スキルの発見機構として、src/agents/skills/ディレクトリをスキャンし、SkillAgentを継承するクラスを自動登録するメカニズムを導入します（Pythonのimportlibまたはパッケージメタデータを使用）。さらに、スキル間の依存関係を宣言的に定義するスキルマニフェスト（skills/manifest.yaml）を導入し、オーケストレーターがこれを解釈して実行順序を決定するようにします。

マニフェストの例：
```yaml
skills:
  - name: CulturalComplianceChecker
    class: src.agents.skills.cultural_compliance.CulturalComplianceChecker
    depends_on: [BibleAgent, ContextBuilderAgent]
    runs_after: [WritingAgent]
    runs_before: [AuditAgent]
    config:
      strict_mode: true
      regions: [JP, US, KR]
```

これにより、新しい「歴史小説のための時代考証エージェント」を追加する場合、src/agents/skills/historical_accuracy.pyに実装し、manifest.yamlに適切な依存関係を記述すれば、自動的に適切な実行フローに組み込まれます。同様に、「BL作品のための関係性描写専門エージェント」や「教育コンテンツのための事実検証エージェント」など、ドメイン固有の要件への対応が劇的に容易になります。

さらに、スキルのバージョン管理とホットスワップをサポートすれば（例えば、skills/v1/とskills/v2/ディレクトリを用意し、設定でバージョンを切替）、運用中のシステムを停止せずに機能アップデートが可能となり、A/Bテスト（新しい創造性評価アルゴリズム vs 旧アルゴリズム）や段階的機能リリースも容易になります。このアーキテクチャにより、研究チームは核となるオーケストレーションロジックを変更することなく、専門的な機能実験を行えるようになり、イノベーションの速度が向上します。

## 5. ソーシャルメディア風相互作用によるキャラクタ関係モデリング強化

現在のBibleAgentはキャラクターの静的プロパティと関係性ラベル（友好・敵対等）をグラフとして保存していますが、関係性の質的側面（感情の変化・信頼度の推移・誤解の生成過程・権力ダイナミクス）を捉える仕組みが不足しています。Constella論文（2025年）のFRIENDS DISCOVERY、JOURNALS、COMMENTS機能は、キャラクター間の関係性を動的かつ多層的にモデリングする効果的アプローチです。

ソーシャルメディア風相互作用では、キャラクターをソーシャルネットワークのノードとして扱い、以下の三つのメカニズムを通じて関係性を動的に更新します：

1. **FRIENDS DISCOVERY**：特定キャラクターに関連する新規キャラクターをAIが生成し、関係性グラフに追加します。例えば、「主人公の親友」から「親友のかつての恋人」や「主人公の師匠のライバル」を発見させることで、世界観の自然な拡張と関係性の複雑化を促進します。

2. **JOURNALS**：共有テーマ（例：「昨日の戦闘」「母親の死」「昇進試験」）に基づき、複登場人物の内面独白・日記エントリ・手紙・映像記録などを生成し、同じイベントに対する異なる視点、感情反応、解釈を明らかにします。これにより、単一の出来事でもキャラクターごとに異なる意味付けがあることを示し、関係性のすれ違いや誤解の元を作り出します。

3. **COMMENTS**：あるキャラクターのジャーナルエントリに対して、他キャラクターが反応・返信・リアクションを行うシミュレーションを実施し（いいね、コメント、リプライなどの形で）、関係性の緊張度・共感度・誤解の生成プロセス・修復の試みを可視化します。例えば、主人公の日記に「今日も失敗だった」という投稿に対して、ライバルが「まあね」とコメントし、親友が「大丈夫だよ」と返すようなやりとりを生成します。

実装では、src/agents/bible.pyにSocialInteractionManagerクラスを追加し、WritingAgentの本文生成完了をトリガーとしてこれらの機能を実行します。具体的には、writing.completedイベントを監視し、現在のシーンに登場するキャラクター群に対してJOURNALS生成を依頼します。生成されたジャーナルは、一時的なノードとしてGraphRAGナレッジグラフに追加され（ノードタイプ：journal_entry、属性：character_id, scene_id, theme, content, timestamp）、次回のContextBuilderAgentによる文脈抽出時に関連情報として参照可能になります。

続いて、これらのジャーナルエントリに対するCOMMENTSシミュレーションを実施します。各ジャーナルに対して、関連性が高い他キャラクター（共登場人物・関係グラフで近いノード）からの反応を生成し、これもナレッジグラフにエッジとして追加します（エッジタイプ：comment_on、属性：reacting_character, sentiment, response_type, content）。

これにより、単なる「友好度80%」という静的値ではなく、「第5話の裏切りイベント後に信頼度が30%に低下し、第8話の共同作業により60%に回復し、第10話の誤解が解けて90%になる」という動的な関係性推移を時系列グラフでモデル化できるようになります。さらに、これらのインタラクションデータを蓄積すれば、読者が共感しやすい関係性の発展パターン（例：信頼の失墜とゆっくりとした修復、最初の嫌悪感からの理解への転換など）を分析し、PlotAgentのカタルシス設計やテンションカーブ生成、およびWritingAgentの感情描写生成にフィードバックループを構築できるようになります。

特に、マルチブランチストーリー（IFルート分岐）においては、各分岐でのキャラクター選択（助ける vs 助けない、許す vs 許さない等）が関係性グラフに与える影響をシミュレーションし、「この選択によりキャラクターXの信頼度が永久に50%以下になる」等の長期的影響を定量的に評価できるようになります。これにより、作者は異なる選択肢の感情的インパクトを理解した上で、物語の分岐点を設計できるようになります。

## 6. DAGベースハイブリッドバッチタスクスケジューリングの導入

現在のHueyタスクキューは基本的にFIFOまたは優先度ベースのキューイングであり、独立したタスクでもキューの順番待ちが発生し、特にGPUを使用する画像生成タスクとLLM推論タスクが混在すると、リソースの未利用が生じています。フィクショナルワールドビルディング論文のDAGベースハイブリッドバッチタスクスケジューリングは、タスク間の依存関係を尊重しながら並列実行を最適化し、処理遅延を最小化する有効な方法です。

DAGベーススケジューリングでは、タスクを有向非巡回グラフとしてモデル化し、各ノードがタスク（例：WritingAgent_task_chapter3、IllustrationAgent_task_chapter3）、エッジが依存関係（例：WritingAgent_task_chapter3 → IllustrationAgent_task_chapter3 は「本文が完成してから挿絵生成開始」）を表します。スケジューラーは、親タスクの完了状況を監視し、依存条件を満たしているタスク（親タスクが全て完了）を並列実行可能なワーカープールに割り当てます。

実装では、src/backend/tasks/dag_scheduler.pyに新しいスケジューラークラスを追加し、既存のHueyConsumerラッパーとして機能させます。タスクの依存関係は、generation_tasks.pyのタスク定義時にメタデータとして付与します（@task(binds=['writing_result'], dependencies=['writing_chapter_3']) といった形で）。スケジューラーは起動時にすべての登録タスクをスキャンし、依存グラフを構築し、準備完了タスクのキューを維持します。

ワーカープールのサイズは、システムリソース（CPUコア数、GPUメモリ、メモリ帯域幅）とタスクタイプに基づいて動的に調整可能とします。具体的には：
- LLM推論タスク：CPUとメモリを主に使用 → ワーカー数 = CPUコア数 × 0.8
- 画像生成タスク：GPUメモリを大量消費 → 同時実行数 = GPUメモリ / タスクあたり必要メモリ（例：8GB GPUでタスクあたり2GBなら4つまで）
- 軽量タスク（データベース更新、簡単な変換等）：ほぼ制限なし

さらに、ハイブリッドアプローチとして、同一ワークフロー内の連続タスク（例：同じ章の執筆→監査→挿絵）については、コンテキストスイッチコスト（LLMのプロンプト再構成、データのシリアライズ/デシリアライズ）を考慮し、可能な範囲でバッチ処理を適用します（同じワークフローのタスクは同じワーカーで連続実行）。一方、異なるワークフロー間のタスク（例：第3章の執筆と第5章のプロット設計）については、リソースが許す限り最大限の並列化を図ります。

これにより、マルチエージェントパイプラインのスループットが理論的にはワーカー数に比例して向上し（独立タスクについては線形スケーリング）、特に長編制作時の全体生成時間が短縮されます（例：10章の同時制作において、従来の順次処理では10時間かかっていたものが、並列処理により2-3時間に短縮可能）。また、タスクの失敗時には、影響を受ける下流タスクのみを自動的にリトライさせる細粒度のエラー回復メカニズム（例：IllustrationAgentの失敗は、同じ章のWritingAgentには影響せず、該当章のIllustrationAgentタスクのみをリトライ）を実装でき、システム全体の堅牢性も向上します。

このスケジューラーは、既存のHueyインターフェースをラップする形で実装すれば、移行コストを最小限に抑えることができます。タスク定義側では@taskデコレータにdependencies引数を追加するだけで、スケジューラーが自動的に依存関係を解釈して最適な実行順序を決定します。

## 7. 反射的スクリーニングによるRAG精度向上

現在のRAGパイプラインは、ユーザークエリまたは執筆コンテキストに基づいてベクトルストアから類似ドキュメントを取得し、プロンプトに注入していますが、取得結果の文脈適合性を評価するフィードバックループが欠如しているため、表面的には類似しているが執筆シーンと目的がずれている情報がプロンプトに混入し、生成品質のばらつきや幻覚（hallucination）を引き起こす可能性があります。DeepWriterのWriteBotコンポーネントにおける反射的スクリーニング機構は、検索結果の関連性と文脈適合性をIteratively評価し、クエリを精緻化することでRAGの精度を向上させる効果的アプローチです。

反射的スクリーニングでは、以下のプロセスを最大T回（例：T=3）反復実行します：
1. **初期検索**：現在のクエリでベクトルストアからTop-Kドキュメントを取得（K=10程度）
2. **関連性評価**：各取得ドキュメントに対して、クエリとのコサイン類似度に加えて、執筆シーンの目的（例：「戦闘シーンの臨場感ある描写」 vs 「キャラクターの内面的葛藤の描写」）とのセマンティック類似度を評価（軽量なタスク特化分類器またはプロンプトベースのLLMジャッジを使用）
3. **文脈適合性評価**：取得ドキュメントが示唆する情報（例：「特定の魔法システムのルールA」）が、現在のWorld Bibleの状態（GraphRAGクエリで「魔法システムAは現在禁止されているか？」等）と矛盾していないかを検証
4. **低スコアフィルタリング**：関連性スコア＋文脈適合性スコアがしきい値未満のドキュメントを除去
5. **クエリ精緻化**：残りの高スコアドキュメントからTF-IDFまたはKeyBERTでキーフレーズを抽出（例：「火属性魔法」「消費MP」「詠唱時間」等）し、これらを元クエリに追加してより具体的なクエリを作成
6. **再検索**：精緻化されたクエリでベクトルストアから再検索を実行

このプロセスを繰り返すことで、徐々にクエリが執筆シーンの真の情報ニーズに特化していき、最終的に高関連性かつ高文脈適合性の情報のみを取得できるようになります。

実装では、src/services/rag_service.pyのretrieve_contextメソッドを拡張し、反射的スクリーニングロジックを組み込みます。関連性スコアの評価には、文意埋め込みモデル（sentence-transformers/all-MiniLM-L6-v2）を使用したコサイン類似度に加えて、軽量なタスク特化分類器を導入します。この分類器は、「クエリの意図」と「ドキュメントの内容」のマッチ度を予測するように事前に訓練しておき、訓練データはAutoNovelの過去の生成ログと人間による評価から作成します。

文脈適合性スコアの評価では、取得ドキュメントから抽出された事実（「魔法AはMPを10消費する」）を、GraphRAGクエリ（「現在の世界観で魔法Aは使用可能か？禁じ手か？」）で検証します。矛盾が検出された場合は、文脈適合性スコアを大幅に減点します。

クエリ精緻化ステップでは、フィルタリングされたドキュメントからKeyBERT（または似たモデル）でキーフレーズを抽出し、これらをAND条件で元クエリに追加します。例えば、元クエリが「魔法システムについて」だったものが、「魔法システム AND 消費MP AND 詠唱時間 AND 火属性」のように精緻化されます。

これにより、関連性が高くかつ文脈適合性の高い情報のみをプロンプトに注入できるため、生成されるテキストの事実正確性と世界観整合性が向上します。特に、長編シリーズでは過去エピソードの膨大な情報量の中から、現在のシーンに本当に必要な制約や伏線を精密に抽出できるため、後世の展開で無理なく利用できる情報の質が向上し、プロットの信頼性が高まるだけでなく、読者が「前回の設定と矛盾していない」と感じられる一貫性ある物語体験を提供できるようになります。

## 8. BookScoreに基づく統一100点尺度の成熟度評価メトリクス実装

現在のAutoNovelにはAuditAgentによる個別の品質スコアは存在しますが、これらは異なるスケールかつ独立しており、全体的な manuscrit 成熟度を一元的に把握する指標が欠如しています。これにより、改善の優先順位付けや進捗の定量的評価が困難になっています。DeepWriter論文のBookScoreは、構造・coherency・factual grounding・visual-textual synergy・読者体験の五つの次元を統合した100点満点の尺度であり、客観的評価と改善サイクルの指標として機能します。

BookScoreの算出方法は以下の通りです：
- **構造スコア（25点）**: プロットツリーの論理的流れ（因果関係の適切性）、章構成のバランス（導入・展開・転結の配分）、テンポの変化（起承転結の明確さ）を評価。PlotAgentの出力と生成された本文を比較して、プロット通りに進行しているかをチェック。
- **coherencyスコア（25点）**: キャラクターの口調一貫性（一人称/三人称の維持、年齢・立場に応じた語彙）、世界観ルールの遵守（魔法システム、技術レベル、社会制度）、タイムラインの一貫性（出来事の順序・時間経過の適切性）、固有名詞の表記統一を評価。主にAuditAgentの一貫性関連モジュールが担当。
- **factual groundingスコア（20点）**: GraphRAG参照情報との整合性（抽出した設定が正しく反映されているか）、歴史・文化的正確性（時代考証、文化的慣習の適切性）、用語の適切性（専門用語の定義と使用）を評価。RAGシステムから取得した情報と本文の記述を照合。
- **visual-textual synergyスコア（15点）**: 挿絵プロンプトと本文描写の情報量マッチ度（同じシーンを描いているか）、焦点の一致（本文で強調している要素が挿絵でも強調されているか）、感情トーンの整合性（悲しいシーンの挿絵が暗い色調か）を評価。IllustrationAgentの出力と本文を比較。
- **読者体験スコア（15点）**: 冒頭のフック強度（読者の注意を引く「謎・違和感・危機」の程度）、末尾の引き（次話への期待感・未解決の要素）、感情曲線の適切性（カタルシスのタイミングと強さ、感情の起伏のバランス）を評価。専門的読者フックオーディターと感情曲線オーディターが担当。

各次元のスコアは0-100点で評価し、重み付けして合計点（0-100）を算出します。重みは作品ジャンルや制作フェーズに応じて動的に調整可能とし、設定ファイル（config/book_score_weights.yaml）で管理します。たとえば、企画段階では構造スコアの重みを高くし、執筆中期ではcoherencyとfactual groundingの重みを増やし、クライマックスでは読者体験スコアの重みを上げます。

実装では、src/services/book_score_service.pyにBookScoreCalculatorクラスを追加し、評価結果をデータベースのbook_scoresテーブルに保存します（カラム：book_id, chapter_number, overall_score, structure_score, coherency_score, factual_grounding_score, visual_textual_synergy_score, reader_experience_score, evaluated_at, evaluator_version）。このスコアは、以下の場面で活用できます：

1. **PlanningAgentの企画評価**: 3案企画ガチャの各案について、プロットアウトラインから構造スコアと読者体験スコアの予測値を算出し、潜在的なBookScoreを見積もる
2. **WritingAgentの生成フィードバックループ**: 生成された本文のBookScoreがしきい値（例：70点）を下回った場合、低スコアだった次元に特化した自動的な再生成トリガーを発動（例：coherencyスコアが低い場合は、ContextBuilderAgentの情報抽出を見直す）
3. **ユーザー向け進行状況表示**: Studioワークスペースでのリアルタイム品質フィードバックとして、現在の章のBookScoreと次元別スコアを表示し、改善すべき点を可視化
4. **自動的な昇格判定**: かんたんモードから上級者Studioへの昇げ推奨基準として、過去3章の平均BookScoreが80点以上かつ向上傾向にある場合を条件とする
5. **改善の優先順位付け**: 次元別スコアが特に低い場合（例：visual-textual_synergy_scoreが50点以下）は、関連する機能（IllustrationAgentのプロンプトエンジニアリング）を優先的に改善対象とする

さらに、BookScoreの時系列変化を追跡すれば、特定のエージェントやプロンプトの改善が全体品質に与える影響を定量的に評価できるようになります。例えば、新しいIllustrationAgentのプロンプトエンジニアリングが挿絵関連スコアにどのように寄与したかを、他のスコアが安定している状態で分析可能になります。これにより、エンジニアリングの意思決定がデータドリブンになり、属人的な「良さ」の判断から脱却し、継続的な改善サイクル（Plan-Do-Check-Act）を確立できます。

## 9. マルチモーダルエンリッチメントの統合

現在のマルチメディア生成は主に本文からシーンを抽出して挿絵プロンプトを生成する一方向きのプロセスであり、生成されるテキスト自体に情報を豊かにする機構が不足しています。DeepWriterのRich Information Insertionフェーズは、文脈に合ったトリビア・引用・画像等のマルチモーダル要素を自動的に挿入し、情報豊かで読者参加型の出力を生成する効果的アプローチです。

マルチモーダルエンリッチメントでは、執筆プロセスのさまざまな段階で以下のような要素を自動的に付加・統合します：

1. **コンテキストトリビア挿入**: GraphRAGから取得した世界観設定や歴史的事実のうち、現在のシーンに関連性が高いが本文では言及されていない雑学を、自然な会話やnarrationの一部として挿入します。例えば、旅行シーンでの土地の由来説明（「この街は紀元前時代に築かれた要塞都市で、石畳はローマ時代のものだ」）、戦闘シーンでの武器の歴史的背景（「この剣は十字軍時代の典型的なロングソードだ」）、料理シーンでの食材の産地情報など、読者に「なるほど」と思わせる雑学を自然に組み込みます。

2. **引用・典拠付与**: 事実記述や歴史的参照に対して、World Bible内の設定資料を参照元として脚注形式で付与し、情報の信頼性を向上させます（例：「『世界観設定書・巻III』p.45より」や「古文書『東国紀行』によれば」など）。これにより、フィクションでありながらも「この世界にはこういう設定資料がある」というメタレイヤーを作り出し、没入感を高めます。

3. **感覚詳細の拡充**: 五感推敲ツールバーの機能を自動化し、抽象的な感情描写（「彼は悲しかった」）を具体的な感覚詳細（「彼の頬を伝う冷たい涙が、石畳の凍りついた感覚を鋭く際立たせた」「遠くから聞こえるサイレンの音が、彼の緊張をさらに高めていた」「革の手袋のざらつきが、剣の hilt をしっかりと捉えていることを伝えた」）に変換します。これにより、「見せるな、語るな」（Show, Don't Tell）の原則を効果的に適用し、読者の感情移入と場面の臨場感を向上させます。

4. **マルチメディアシナリオ生成**: 本文の重要シーンから、マンガ台本・ラジオドラマ脚本・アニメ絵コンテ・ライブアクションのショットリスト等の派生作品のための構造化アウトラインを自動生成します。例えば、クライマックスの戦闘シーンから、コマ割り・セリフ・効果指示・カメラワークを含むマンガのネームを生成したり、重要な対話シーンからラジオドラマ用の音響指示と声優演技ノートを作成したりします。

実装では、src/agents/enrichment_agent.pyに新しいEnrichmentAgentを追加し、マルチエージェントオーケストレーションフローのWritingAgentとAuditAgentの間に挟みます（WritingAgent → EnrichmentAgent → AuditAgent）。EnrichmentAgentは、WritingAgentの出力を入力として受け取り、以下の処理を実行します：

1. **情報抽出**: GraphRAGとVectorStoreから現在のシーンに関連するエンティティ・事実・設定・歴史情報を抽出します（クエリ例：現在の場所に関する歴史、登場しているアイテムの由来、関係している勢力の背景等）
2. **関連性フィルタリング**: 抽出結果のうち、本文中に明示されていないが文脈を豊かにする情報をLLMベースの重要度判定器でフィルタリングします（「この情報は現在のシーンの理解を深めるか？」「読者の没入感を高める可能性があるか？」等を判定）
3. **自然な組み込み**: 選択された情報を、本文の文体・視点・時制に合わせて自然な形でテキストに組み込みます（テンプレートベースまたは生成AIを用いた言い換え）。例えば、三人称過去形の narration なら「歴史的には…」という形で、第一人称なら「私は知っていたが…」という形で組み込みます。
4. **付記形式決定**: 組み込んだ情報に対して、適切な付記形式（脚注・括弧注・対話内説明・ナレーション内補足）を決定します。学術的・説明的な情報は脚注、会話に自然に組み込めるものは対話内説明、雑学的なものは narration 中の一言とし、文体の一貫性を保ちます。

これにより、読者は本文を読むだけで世界観の深さや設定の一貫性を体感できるようになり、別途設定集を参照する必要が減少します。さらに、生成されたエンリッチメント済みテキストを基にIllustrationAgentが挿絵プロンプトを生成すれば、本文と挿絵の情報量と焦点がより一致し（本文に豊富な歴史的背景があるなら、挿絵にも時代考証された衣装や建築様式を反映しやすくなる）、マルチメディア適合性スコアの向上にも寄与します。

特に、教育的要素や歴史小説においては、エンターテインメントと知識の伝達を自然に融合させることが可能となり（例：戦国時代の小説で、合戦の合間に当時の農村生活や城下町の経済についてのトリビアを挿入）、AutoNovelの適用領域を純粋なフィクションからエドューテイメントへと拡張できるようになります。これにより、「楽しく読んで、かつ何か学べる」という新しい価値提案が実現できます。
