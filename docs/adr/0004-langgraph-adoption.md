# ADR-0004: LangGraph 採用理由

**日付**: 2026-08-16
**ステータス**: 採用済み
**決定者**: 開発チーム

## 背景

覇権小説エンジンでは、小説生成パイプライン（企画→プロット→執筆→監査→リライト→完結）をオーケストレーションする必要があった。従来は自作の非同期パイプライン（`asyncio` + カスタム状態管理）を使用していたが、以下の課題があった。

## 課題

1. **状態管理の複雑性**: 各ステップ間のデータ受け渡し、エラーハンドリング、リトライ、キャンセル処理を自前で実装していた
2. **可視化・デバッグ困難**: 実行フローの可視化、中間状態のインスペクション、再実行ポイントの指定が困難
3. **並列・分岐処理の限界**: 条件分岐、並列実行、人間レビューゲート等の高度なワークフロー制御が実装コスト高
4. **拡張性**: 新しいステップ追加や既存ステップ置換時の影響範囲が大きい

## 検討した選択肢

| 選択肢 | メリット | デメリット | 判定 |
|--------|----------|------------|------|
| **自作パイプライン継続** | 完全制御、依存ゼロ | 上記課題解決に工数大 | 却下 |
| **Airflow/Prefect** | 本番実績豊富、UI充実 | 重い、オーバーヘッド大、ローカル開発不向き | 却下 |
| **Temporal** | 耐障害性高、長時間実行向け | 運用コスト高、学習曲線急 | 却下 |
| **LangGraph** | LangChain生態系、グラフベース状態管理、ストリーミング対応、軽量、Python標準的 | 比較的新しい、ドキュメントまだ充実途上 | **採用** |
| **自作 + LangGraph ハイブリッド** | 段階的移行可能 | 二重管理の複雑性 | 却下 |

## LangGraph 採用の決定理由

### 1. グラフベースの状態管理
- `StateGraph` でノード（ステップ）とエッジ（遷移）を宣言的に定義
- 共有状態 (`TypedDict`/`Pydantic`) で型安全なデータ受け渡し
- 条件分岐 (`add_conditional_edges`) が直感的

### 2. 組み込み機能で実装コスト削減
| 機能 | 自作実装工数 | LangGraph |
|------|-------------|-----------|
| チェックポイント/再開 | ~200行 | `MemorySaver` / `SqliteSaver` |
| ストリーミング出力 | ~100行 | `astream` / `astream_events` |
| 人間介入ゲート | ~150行 | `interrupt` / `Command(resume=...)` |
| 並列実行 | ~100行 | `Send` API / ファンアウト |
| リトライ/タイムアウト | ~100行 | `RetryPolicy` / 設定 |

### 3. 開発体験 (DX) 向上
- `langgraph-studio` でローカル可視化・デバッグ
- 中間状態のタイムトラベル確認可能
- 単体テストでノード単体実行容易 (`graph.invoke({...})`)

### 4. 既存資産との親和性
- `LangChain` プロンプトテンプレート (`PromptTemplate`)、LLMクライアント (`ChatGoogleGenerativeAI` 等) とシームレス連携
- `Runnable` インターフェースで既存コンポーネントをノード化容易

### 5. 軽量・依存最小
- Core: ~5000 行、依存: `langchain-core`, `pydantic`, `typing-extensions` のみ
- 本番デプロイで追加コンテナ不要 (Airflow/Prefect/Temporal と違い)

## 実装への影響

### 移行範囲
- `src/backend/workflows/`: 全ワークフローを LangGraph 化
- `src/easy_mode/pipeline.py`: オーケストレーション部分を `StateGraph` に置換 (Step 実装は既存関数をノード化)
- 状態定義: `EasyModeState` / `WritingState` 等を `TypedDict` で型定義

### 非採用部分
- LLM 呼び出し自体は従来通り `LLMGenerateResultProxy` 使用 (LangGraph 依存させない)
- プロンプト構築は既存 `PromptManager` / Jinja2 継続
- DI コンテナ (`AppContainer2`) からノード関数取得しグラフ構築

## リスクと対策

| リスク | 対策 |
|--------|------|
| API 変更・破壊的変更 | `langgraph` バージョン固定 (`~=0.2`)、破壊的変更時はメジャーバージョンアップで対応 |
| デバッグ時のスタックトレース複雑 | `langgraph-studio` 活用、ログ出力強化 |
| 学習コスト | 内部ドキュメント化、サンプルコード整備、ペアプロで知見共有 |

## 代替案の再評価タイミング

- v4.0 リリース時、または LangGraph に致命的問題発生時
- 代替: `Prefect` (Python ネイティブ、軽量化進んでいる) または自作ステートマシン回帰
