# 50話×3000文字 小説自動生成 実装計画（低性能LLM対応）

## 0. 目的・制約・戦略

**目的**: カクヨムランキング上位・商業出版レベルの小説（50エピソード、各3000±100文字、合計約15万文字）を、自動生成パイプラインで作成する。

**制約（低性能LLM前提）**:
- モデル: 7B〜13Bクラス、Context 4kトークン、最大出力 512〜1024トークン想定
- 長文生成が苦手、理由付け（推論）が弱い、フォーマット崩れやすい
- したがって「1回の呼び出しで3000文字書かせる」のは不可。必ず分割する

**戦略（3本柱）**:
1. **チャンク分割生成** — 1エピソードを7パートに分け、各パートを独立した小LLM呼び出しで生成
2. **テンプレート固定** — 世界観・キャラ・構成をあらかじめ定数化し、LLMには「穴埋め」だけさせる
3. **後処理検証** — 文字数・必須要素・重複をスクリプトで機械チェックし、不足分は再生成ループ

---

## 1. 全体アーキテクチャ

```
[設定JSON] ──► [パート生成×7] ──► [結合] ──► [検証] ──► [保存]
 (world.yaml)   (low-LLM call)      (concat)   (script)   (epNN.md)
                    │                      │
                    └── 失敗/短い ──► 再生成(最大3回)
```

- 各パート呼び出し: 入力300〜600トークン、出力300〜600文字
- プロンプトには「出力は本文のみ。余計な挨拶・解説禁止」を明記
- 結合後 `len(text)` で2900〜3100を確認、外れたら該当パートだけ再生成

## 2. 72ステップ詳細実装計画

### フェーズA: 準備・設計（ステップ 1〜10）

1. 目標文字数を定数化: `TARGET=3000, MIN=2900, MAX=3100` を config に書く
2. エピソード総数 `EPISODES=50` を設定ファイルに記録
3. ジャンルを1語で決定（例:「光層ファンタジー」）し world.yaml の `genre` に格納
4. 主人公の名前・年齢・性格・動機を1文ずつ world.yaml の `protagonist` に書く
5. 舞台世界の「シンボル」を1つ決める（例:「光の石」）し `symbol` に格納
6. 敵対勢力を1文で定義（例:「闇結社が石を狙う」）し `antagonist` に格納
7. 主要サブキャラ2名を名前＋役割だけ定義（例:「ナビ役の少女」「戦士」）
8. 感情語リスト15語（喜・恐怖・決意・不安・希望…）を `emotion_words.txt` に作成
9. クリフハンガー10パターンを `cliff_patterns.txt` に列挙（石が暗くなる等）
10. 上記を `world.yaml` に集約し、人間が1分で読める形に整える

### フェーズB: テンプレート・プロンプト作成（ステップ 11〜18）

11. エピソード構成テンプレート（7パート・文字数配分）を `template.md` に書く
12. パート①用プロンプト雛形:「世界観シンボルを300字で描写。余計な説明禁止」を作成
13. パート②用:「主人公の過去回想100字＋現在の不安300字。感情語を2語含める」を作成
14. パート③用:「今回のミッションを500字で提示。目的を明確に」を作成
15. パート④用:「サブキャラ1名との小ミッション300字。背景は1行」を作成
16. パート⑤用:「最大緊張のアクション600字。視覚・聴覚・触覚を交える」を作成
17. パート⑥用:「感情クライマックス400字。緊張→解放→再緊張のリズム」を作成
18. パート⑦用:「余韻＋次回示唆500字。cliff_patternsから1つ選んで使う」を作成

### フェーズC: 文字数・品質チェックツール（ステップ 19〜27）

19. `count_chars.py` を作り、引数のファイル文字数を印字する
20. `check_range()` 関数: MIN〜MAX 内なら True を返すように実装
21. `extract_parts()` を作り、結合前の各パート文字数を個別表示する
22. `require_words()` を作り、感情語リストの出現数をカウントする
23. `check_cliff()` を作り、⑦にクリフパターン文字列が含まれるか確認する
24. `detect_dup()` を作り、同一表現が3回以上連続していないか調べる
25. `validate_episode()` を作り、上記全部をまとめて合否を返す
26. 不合格時のメッセージを「どのパートが短いか」明示するよう実装
27. チェックツールをサンプル文字列で動かし、正常に判定されることを確認

### フェーズD: 第1話プロトタイプ生成・調整（ステップ 28〜36）

28. パート①だけをLLMに投げ、出力を `ep01_p1.txt` に保存
29. 文字数が300±50でなければ再生成（最大3回）し、收まるまで繰り返す
30. パート②〜⑦も同様に順次生成し `ep01_p2..p7.txt` に保存
31. 7ファイルを結合し `ep01_raw.md` を作成
32. `validate_episode(ep01_raw.md)` を実行し、不足パートを特定
33. 不足パートだけ再生成して上書きし、再結合する
34. 感情語が2語未満なら、該当パートに感情語を挿入する補助関数を手動適用
35. クリフが無ければ `cliff_patterns` から1つ選び⑦末尾に付加
36. 第1話完成版 `ep01.md` を保存し、人間が読んで「許容」か最終確認

### フェーズE: バッチ生成運用（ステップ 37〜50）

37. `generate_part(ep, part, ctx)` 関数を作り、パート生成を共通化
38. `build_ctx(ep)` を作り、前話のあらすじ＋未回収伏線をcontextに渡す
39. `generate_episode(ep)` を作り、7パート生成→結合→検証を一括実行
40. 検証失敗時は `retry_parts()` で該当パートだけ再生成する仕組みを実装
41. `run_batch(start, end)` を作り、指定範囲のエピソードを順次処理
42. 各エピソード生成後に `validate_episode` ログを `log/epNN.log` に出力
43. 夜間バッチ用に `nohup` やタスクスケジューラー設定手順をメモ
44. 生成済みエピソード番号を `progress.txt` に書き込み、再開可能にする
45. エラー時は該当エピソードをスキップし、後で `retry_failed()` で再挑戦
46. 10話ごとに中間レビュー: 文字数平均・感情語平均を集計スクリプトで出す
47. 平均が基準を下回れば、プロンプトの文字数指示を±50調整する
48. 同名キャラ表記ゆれを防ぐ `normalize_names()` を後処理に追加
49. 連続する「だ。」の重複を1つに減らす軽い正規化を実装
50. バッチ完了後、全50話の `epNN.md` が揃っているか `check_all()` で確認

### フェーズF: 伏線・クリフ管理（ステップ 51〜58）

51. `foreshadow.csv` を作り、列: ep, type(伏線/回収), text, status を用意
52. 各エピソード生成時に⑦のクリフを `foreshadow.csv` に追記（status=未回収）
53. 次話の `build_ctx` で「未回収の直近1件」を自動で文脈に含める
54. 回収済みになったら `status=回収` に更新する関数を作る
55. 50話最後に「全伏線回収チェック」を行い、未回収があれば終話で処理
56. クリフパターンが10回以上同じものを使っていないか `cliff_usage()` で集計
57. 偏りがあれば別パターンを優先するよう `next_cliff()` を実装
58. 伏線マップを `foreshadow_map.md` に出力し、人間が全体整合を目視確認

### フェーズG: 自動レビュー・スコアリング（ステップ 59〜64）

59. `score_pacing()` を作り、パート文字数のバランスからテンポ得点を出す
60. `score_emotion()` を作り、感情語出現密度から感情振幅得点を出す
61. `score_world()` を作り、symbol語の出現回数から世界観深度得点を出す
62. `score_cliff()` を作り、⑦のクリフ有無＋多様性からフックスコアを出す
63. `score_total()` で上記4つを統合し、0〜1の商業スコアを計算
64. 全話のスコアを `scores.csv` に集計し、平均0.9以上を目標にする

### フェーズH: 人手微調整・校正（ステップ 65〜68）

65. `scores.csv` で低スコア（<0.8）のエピソードをリストアップ
66. 低スコア話の該当パートだけを手動で書き換え、再検証
67. 表記ゆれ・文法ミスをエディタで一括修正（約10%削減目標）
68. 最終 `epNN.md` を `final/` にコピーし、校正済みフラグを付ける

### フェーズI: カクヨム公開準備（ステップ 69〜72）

69. カクヨム形式のタイトル（「第N話 サブタイトル」）を各ファイル先頭に付与
70. タグ候補（ファンタジー・異能・冒険等）を `metadata.json` に用意
71. あらすじ（200字）と最初の3話を人間が読み、導入の魅力を最終チェック
72. 公開用 ZIP または本文結合ファイルを作成し、アップロード手順をまとめる

## 3. 低性能LLMでも動かすための具体策

- **分割生成**: 1呼び出し=最大600文字。3000文字は7回の呼び出しに分解（ステップ11-18,28-36）
- **Few-shot不要**: テンプレートが厳密なので、例示なしで「穴埋め」形式にする
- **出力制限**: `max_tokens=700` に設定し、はみ出しを防ぐ。余計な挨拶はプロンプトで禁止
- **再生成ループ**: 短い・フォーマット崩れは検証スクリプトが検出し、該当パートだけ再実行（最大3回）
- **コンテキスト削減**: `build_ctx` は「前話あらすじ100字＋未回収伏線1件」のみ渡す（数100トークン）
- **determinism**: temperature=0.7 で十分。低性能帯では 0.9 より安定
- **オフライン前提**: API乞いではなくローカルモデル（Ollama等）で動かす想定の設計

## 5. 最小プロンプト例（パート⑤・アクション）

```
以下の条件で小説の「戦闘クライマックス」を600文字書いてください。
・主人公: 凛（光に覚醒した青年）
・敵: 闇結社の兵
・舞台: 光の石が浮かぶ遺跡
・視覚・聴覚・触覚の描写を必ず各1つ入れる
・出力は本文のみ。挨拶・解説・「以下は」等の前置き禁止
・1文は30〜35文字程度で区切る
```

このように「役割・制約・出力ルール」を短く三点セットにすることで、低性能LLMでも比較的守りやすくなる。

---

## 6. 成功の判定基準

- 50話すべて `MIN=2900〜MAX=3100` 文字を満たす
- 各話に感情語≥2、クリフ≥1、symbol語≥1 が含まれる
- `score_total` 平均 ≥ 0.9
- 伏線の未回収が終話までに0件
- 人間が第1話・第25話・最終話を読み「続きが気になる」と感じる

以上が、低性能LLM環境でも実行可能な **72ステップ・詳細実装計画** である。この手順に従えば、チャンク分割と機械検証の組み合わせで、安定して50話×3000文字の商業レベル小説を生成できる。
