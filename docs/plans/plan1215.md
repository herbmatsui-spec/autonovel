# 改善実装計画書

## 概要
本計画書は、振舞コーディングによる機能喪失を防止するための3つの改善案を詳細な実装ステップに分割したものです。
全24ステップに分け、順次実装することを想定しています。

## ステップ一覧

### フェーズ1: CI/CDパイプラインの修正 (ステップ1-8)

**ステップ1: CIワークフローのバックアップ**
- `.github/workflows/ci.yml` の現在版をバックアップとして `.github/workflows/ci.yml.backup` にコピー

**ステップ2: lintジョブの修正**
- `continue-on-error: true` を削除
- `ruff check` と `ruff format --check` のコマンドから `|| true` を削除し、失敗時にジョブを失敗させる

**ステップ3: typecheckジョブの修正**
- `continue-on-error: true` を削除
- `mypy` コマンドから `|| true` を削除

**ステップ4: black-checkジョブの修正**
- `continue-on-error: true` を削除
- `black --check` コマンドから `|| true` を削除

**ステップ5: test-unitジョブの修正**
- `continue-on-error: true` を削除
- `pytest` コマンドから `|| true` を削除
- カバレッジレポートのアップロードステップは `if: always()` のまま保持（失敗してもアーティファクトを取得するため）

**ステップ6: test-integrationジョブの修正**
- `continue-on-error: true` を削除
- `pytest` コマンドから `|| true` を削除

**ステップ7: test-contractジョブの修正**
- `continue-on-error: true` を削除
- `pytest` コマンドから `|| true` を削除

**ステップ8: その他のジョブの修正と全体テスト**
- `test-migration`, `test-perf`, `frontend-test` ジョブについて同様に `continue-on-error: true` を削除し、`|| true` を削除
- 変更をコミットし、プルリクエストを作成してCIが正常に失敗することを確認（意図的にエラーを入れてテスト）
- エラーを修正し、再度プルリクエストを作成してCIがパスすることを確認

### フェーズ2: プルリクエストレビュープロセスの強化 (ステップ9-16)

**ステップ9: プルリクエストテンプレートの作成**
- `.github/PULL_REQUEST_TEMPLATE.md` を新規作成
- 次項目を含むチェックリストを追加:
  - [ ] テストを追加/更新したか
  - [ ] 変更点の影響範囲をドキュメントに記載したか
  - [ ] 機能フラグがある場合、両状態（ON/OFF）でテストしたか
  - [ ] 既存機能への回帰を防ぐための具体的なテストシナリオを記載したか
  - [ ] パフォーマンスへの影響を考慮したか
  - [ ] セキュリティ観点でのレビュー項目はないか

**ステップ10: テンプレートの利用促進のためのドキュメント更新**
- `CONTRIBUTING.md` の「プルリクエストの作成」セクションを更新し、新しいテンプレートの利用を必須とする旨を記載

**ステップ11: ブランチ保護ルールの設定（リポジトリ設定）**
- GitHubのリポジトリ設定で、`main` と `develop` ブランチに対して以下の保護ルールを設定:
  - プルリクエストによるマージを必須とする
  - 承認が必要なレビュー数を2人に設定
  - 最新の状態に更新することを必須とする
  - ステータスチェックをパスすることを必須とする（CIのすべてのジョブ）
  - 管理者を含むすべてのユーザーに適用

**ステップ12: コードオーナーの設定**
- `.github/CODEOWNERS` を作成または更新し、主要なディレクトリごとにコードオーナーを割り当て
- 例: `src/backend/` `@backend-team`, `frontend/` `@frontend-team`, `tests/` `@qa-team`

**ステップ13: レビューガイドラインのドキュメント化**
- `CONTRIBUTING.md` に「レビューの観点」セクションを追加し、レビュー時に確認すべき項目を列挙
- 例: 
  - この変更で壊れる可能性がある機能は？
  - テストケースは十分か？
  - エラーハンドリングは適切か？
  - パフォーマンスへの影響は？

**ステップ14: 自動ラベリングのためのGitHub Actionの設定**
- `.github/workflows/labeler.yml` を新規作成
- 変更されたファイルに基づいてラベルを自動付与（例: `backend`, `frontend`, `documentation`）
- ラベルに基づいてレビュアーを自動割り当てする仕組みを検討（将来の改善点として）

**ステップ15: プルリクエストテンプレートの試験運用**
- 作成したプルリクエストテンプレートを使って実際にプルリクエストを出し、運用感を確認
- 必要に応じてテンプレートを調整

**ステップ16: レビュー効果の測定指標の定義**
- ドキュメントに以下の指標を追加し、定期的に測定することを決定:
  - プルリクエストあたりの平均レビュー回数
  - マージまでの平均時間
  - リリース後の障害数（機能喪失に関連するもの）
  - これらの指標をダッシュボードに表示するためのissueを作成（将来の改善点として）

### フェーズ3: 本番環境でのインシデント検知強化 (ステップ17-24)

**ステップ17: 本番メトリクスの定義**
- `docs/METRICS.md` を新規作成し、本番で監視すべきメトリクスを定義
- 例:
  - ビジネスメトリクス: 
    - 本生成成功率（1時間あたり）
    - 監査スコアの平均値と分布（BookScore、各専門家スコア）
    - エラーレート（5xxエラー数）
    - ZIP納品リクエスト成功率
  - システムメトリクス:
    - キューの待ち時間（Huey）
    - ワーカーの利用率
    - データベース接続プールの使用率
    - キャッシュヒット率

**ステップ18: Prometheusメトリクスの追加実装**
- ビジネスメトリクスをPrometheusでエクスポートするためのコードを追加
- `src/services/metrics.py` を新規作成し、カスタムメトリクスを定義
- 例: 
  - `book_generation_success_total`
  - `book_score_sum` と `book_score_count`（平均計算用）
  - `audit_score_{dimension}`（各次元のスコア）
  - `zip_delivery_success_total`
- 既存のメトリクスエンドポイント（`/metrics`）にこれらを追加

**ステップ19: メトリクス収集のポイント実装**
- 本生成フローの成功/失敗ポイントでメトリクスをインクリメント
- 監査完了時に各スコアを観測
- ZIP生成エンドポイントで成功/失敗を観測
- これらの実装は既存のサービス（`WritingService`, `AuditService`, `MarketingAgent`等）に追加

**ステップ20: Grafanaダッシュボードの作成**
- `grafana/dashboards/` ディレクトリを作成し、`autonovel-production.json` ダッシュボードを作成
- パネル例:
  - 本生成成功率（時系列）
  - BookScore平均値と分布（ヒストロgram）
  - 各監査次元のスコア平均値
  - エラーレート（5xx/時間）
  - ZIP納品成功率
  - キューの待ち時間とワーカー利用率
- ダッシュボードをGit管理下に置く

**ステップ21: アラートルールの設定**
- `grafana/alerts/` ディレクトリを作成し、重要なメトリクスの変化を検知するルールを定義
- 例:
  - BookScore平均値が過去1時間で10ポイント以上下落したらアラート
  - 本生成成功率が95%を下回ったらアラート
  - エラーレートが通常の2倍以上になったらアラート
  - キューの待ち時間が5分を超えたらアラート
- アラートはSlackやメールで通知するように設定

**ステップ22: カナリアリリースのためのインフラ整備**
- Docker ComposeやKubernetesマニフェストにカナリアデプロイ用のサービス定義を追加
- `docker-compose.canary.yml` を新規作成し、本番環境の一部トラフィックをカナリアにルーティングする設定を含む
- トラフィック分割にはNGINXやIstioなどを使用するが、まずは簡易版としてポート分割で検証

**ステップ23: フィーチャーフラグシステムの導入**
- `src/services/feature_flags.py` を新規作成し、機能フラグを管理する仕組みを実装
- フラグの設定は環境変数または設定ファイルから読み込み
- 主要な機能リリース時にフラグを用いて段階的ロールアウトが可能になるように設計
- 例: 新しい監査アルゴリズムをリリースする際、`NEW_AUDIT_ALGORITHM_ENABLED` フラグでオン/オフを切り替え

**ステップ24: 本番デプロイ手順の更新と訓練**
- `DEPLOYMENT.md` を更新し、カナリアリリースとフィーチャーフラグを用いたデプロイ手順を記載
- アラートが発生した際の対応フローチャートを作成し、ドキュメントに追加
- 四半期に一度のインシデント対応訓練を計画し、今回の改善点を含めたシナリオを作成

## 完了条件
- すべてのステップが完了し、ドキュメントが更新されていること
- CI/CDパイプラインが正常に機能し、意図的なエラーで失敗することを確認済みであること
- プルリクエストテンプレートが運用され、レビューが効果的に行われていること
- 本番メトリクスが収集され、ダッシュボードとアラートが機能していること
- カナリアリリースとフィーチャーフラグの仕組みがテスト環境で動作確認済みであること

## 注意点
- ステップは順不同で実行できるものもあるが、全体の流れを考慮して上記順序を推奨する
- 各ステップの完了後は、可能であれば小さなプルリクエストで変更をマージし、フィードバックを得ること
- 大きな変更は機能フラグで保護し、本番での影響を最小限に抑える
